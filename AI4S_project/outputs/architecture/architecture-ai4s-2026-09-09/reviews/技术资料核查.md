## 2. 权限与后台：框架能力不等于业务授权

Django 核心预留对象权限接口，但默认没有完整对象权限实现。项目成员、来源许可、用途、保护集状态、图谱权益与版本可见性必须由平台授权服务统一判断。[Django 对象权限说明](https://docs.djangoproject.com/en/5.2/topics/auth/customizing/#handling-object-permissions)

DRF 的对象权限不会自动逐条覆盖列表结果，创建动作也需要专门校验；必须在查询集过滤、创建服务、详情读取、下载、搜索与后台任务入口分别接入同一授权规则。DRF API 视图不自动遵循 Django LoginRequiredMiddleware，API 默认认证与拒绝匿名策略需要明确配置。[DRF 权限说明](https://www.django-rest-framework.org/api-guide/permissions/)、[DRF 3.16 公告](https://www.django-rest-framework.org/community/3.16-announcement/)

本项目约束：Django Admin 仅作为内部管理入口，贡献发布、gold 退役、奖励变更、授权撤回等动作必须调用领域命令服务；不得通过普通表单、批量 action 或直接修改状态字段绕过版本检查、审计和事务。`is_staff` 与 `is_superuser` 不能自动获得研究材料外发资格。此处为针对平台要求的架构决定，依据是 Admin 的内部管理定位，而非官方已提供这些业务规则。[Django Admin 定位](https://docs.djangoproject.com/en/5.2/ref/contrib/admin/)

## 3. 后台消息与外部模型调用

RabbitMQ 发布确认丢失、消费者连接断开或任务重投可能导致重复消息，官方要求消费者能处理重复交付。Celery 的延后确认配置要求任务具备幂等性，确认策略也不能消除所有故障窗口。[RabbitMQ 可靠性指南](https://www.rabbitmq.com/docs/reliability)、[Celery 任务文档](https://docs.celeryq.dev/en/stable/userguide/tasks.html)

本项目据此采用以下约束：

- PostgreSQL 保存权威任务和结果状态；消息仅携带任务标识与版本。业务事务内写出站事件，提交后发布；消费者以稳定业务幂等键和数据库唯一约束防止重复结果或重复发奖。
- RabbitMQ 使用持久化队列、持久化消息、发布确认、消费确认及明确重试上限；单节点仍是单故障域，不声称高可用。
- 模型请求使用单独调用账本、预算预留、请求指纹和供应商请求标识。外部请求已发送但响应未知时记为 `outcome_unknown`；不能因队列重投就直接再次付费调用。
- 供应商只有在文档明确支持幂等键且覆盖该接口时才可据此安全重试。否则先查询结果或核对调用记录，再由明确的重试动作产生新尝试与成本记录。
- “数据库业务结果只提交一次”可以用唯一约束和事务实现；“外部模型绝不被调用两次／绝不重复计费”不能由 RabbitMQ 或 Celery 保证。权限在排队、执行前和交付时均复查；过期结果不能覆盖当前版本。

以上是根据交付语义作出的系统设计约束，不是对某家模型供应商接口能力的实测结论。

## 4. RPO/RTO、PITR 与全文文件一致性

PostgreSQL PITR 依赖合格基础备份和从备份起连续可用的 WAL；`pg_dump` 不能替代物理备份加 WAL 的恢复链。归档失败必须监测，不能因配置存在就声称已达到 1 小时 RPO。[PostgreSQL 17 PITR](https://www.postgresql.org/docs/17/continuous-archiving.html)

pgBackRest 负责数据库备份、归档与恢复管理，支持 PostgreSQL 17。过度清除 WAL 会破坏时间点恢复范围；按时间恢复需要可到达该时间点的备份与日志链。[pgBackRest 指南](https://pgbackrest.org/user-guide.html)

本项目实现上还必须单独备份原始全文、导入文件和不可再生附件，并维护 `object_id / immutable_version / hash / size / created_at / backup_verified_at` 清单。数据库备份成功不表示它引用的文件已经进入备份；对象目录复制成功也不表示数据库可恢复到相同时间。

建议实现共同恢复边界：每批文件备份校验后记录清单和覆盖时间，结合已验证的 WAL 可恢复时间确定最近一致恢复点；恢复时先核对数据库引用的对象是否齐全、哈希是否一致。文件采用不可变版本，物理清理必须考虑当前引用、恢复期和备份保留要求。缺少文件时不得把对应证据任务标为完整成功。

1 小时 RPO 与 4 小时 RTO 是用户确认的验收目标，不是当前达到的指标。单服务器整机损坏场景需要异机备份目的地、可重建环境及一次完整演练；同机另一个容器或磁盘目录不能独立覆盖整机丢失。恢复后还须处理撤权、删除墓碑、外部调用未知结果和事件重投，避免旧备份重新开放已禁止访问的材料。

## 5. 文字 PDF 的解析边界

pypdf 不是 OCR 软件；扫描图像可能返回空文本。PDF 没有保证正确的段落语义、阅读顺序、空格或表格结构；含 OCR 文本层的文档仍可叠加识别及解析误差。pdfplumber 更适合机器生成 PDF，不能据其抽取成功直接认定证据可靠。[pypdf 文本提取说明](https://pypdf.readthedocs.io/en/stable/user/extract-text.html)、[pdfplumber 官方说明](https://github.com/jsvine/pdfplumber)

首版按用户选择：文字 PDF 自动解析；扫描件、乱码、多栏顺序错误、加密或关键段落缺失进入待人工处理。保存文件哈希、解析器版本、页码和定位范围；人工补录必须保留原文对应位置与核查人。空文本不是“没有研究证据”，解析失败不是“研究空白”。不默认新增 OCR 服务、GPU 推理服务或重复调用两个解析器。

## 6. 开工与上线核查清单

1. 在选定 Linux 镜像内生成后端依赖锁文件和前端锁文件；保存镜像摘要、系统依赖版本及安全扫描结果，禁止生产使用浮动 `latest`。
2. 执行 Django 5.2 / DRF 3.16 / Psycopg 3 / PostgreSQL 17 的认证、权限、事务与迁移测试，以及 Celery 5.6 / RabbitMQ 4.3 的断连、重复投递、任务超时测试。
3. 单独验证 Vue 类型检查、生产构建、图交互上限与真实题录、全文样本解析；版本兼容资料不代替性能和正确性验收。
4. 设组件维护责任人，至少每月检查安全公告。RabbitMQ 4.3 的近期社区支持终点需在上线排期中明确；未完成新受支持系列升级验证时不得延续“受支持部署”结论。
5. 首次邀请用户前完成异机恢复演练，记录最后共同恢复点、实际数据损失和服务恢复耗时。30 天备份保留、30 天删除恢复期与 1 年审计元数据保留应分别验证，不能混为统一文件删除策略。
